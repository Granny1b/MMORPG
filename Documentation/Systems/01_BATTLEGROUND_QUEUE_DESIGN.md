# Battleground Queue and Instance System — Design

**Status:** design only, nothing implemented. Written 2026-09-03.

## Purpose

This document plans a battleground system: players join a queue from anywhere in the world, and
once enough have queued, the server spawns a dedicated instance and pulls them all into it.

It exists because the obvious approach — call the kit's existing `WarpCharacterToInstance` — does
not work for a queue, and the reason is not visible from the API surface. The analysis below was
done against the source in this repository, and every claim carries a `file:line` citation so it
can be re-checked after a kit update.

## Scope

Inside this document:

- What the kit already provides for instanced maps, and the exact shape of it.
- Why the built-in instance warp cannot serve a queue, and the supported way around it.
- The component breakdown, the extension mechanism chosen for each piece, and why.
- Gotchas found in the kit source that will cost time if discovered late.
- A phased build order that puts the riskiest unknown first.

Outside this document:

- The extension mechanisms themselves: `Documentation/EXTENDING.md`.
- Match rules, scoring, class balance, reward tuning. Those are content decisions, not architecture.
- The MMO topology in general: `Documentation/PROJECT_OVERVIEW.md`.

## Prerequisite: this is MMO-mode-only work

**LAN mode cannot do this.** `LanRpgNetworkManager.IsInstanceMap()` returns a hard `false`
(`Core/Scripts/LanGame/Networking/LanRpgNetworkManager.cs:452`), and its
`WarpCharacterToInstance` is a stub that forwards to an ordinary warp, with a kit `TODO`
acknowledging the gap (`:445`).

Real instances exist only in the MMO layer, where an instance is a **separate map-server process**
spawned on demand by the cluster. So the whole feature depends on the MMO topology being live:
central server, cluster, map-spawn server, database server.

Per `CLAUDE.md`, `Assets/UnityMultiplayerARPG/MMO/Demo/Scenes/00Init_MMO.unity` is **not wired to
this project's assets** — it still points at the kit's stock `GameInstance.prefab`, stock database,
stock controller and stock canvas. That wiring is Phase 0 below and is a real prerequisite, not a
detail.

## What the kit already gives us

Three pieces of the puzzle already exist and are solid.

**1. On-demand instance map servers.** A map server asks the cluster to spawn one via
`MMORequestTypes.SpawnMap`; the cluster picks a map-spawn server, boots the process, and replies
with a `CentralServerPeerInfo` — the address and port of the new instance
(`MMO/Scripts/MMOGame/Src/Cluster/ClusterServer.cs:489`).

**2. A warp-to-arbitrary-server primitive.** `SaveAndWarpCharacterByPeerInfo`
(`MMO/Scripts/MMOGame/Networking/Map/MapNetworkManager_PlayerActivity.cs:156`) does the whole
handoff: flags the character as warping, unregisters it, saves it to the database, destroys the
server-side entity, and sends the client an `MMOWarpMessage` pointing at the new host. This is
exactly the operation a battleground needs, once per participant.

**3. Custom map types with their own rules.** `BaseMapInfo` is abstract and its behaviour is
virtual, so a battleground map can define its own spawn placement, respawn policy and PvP rules
without touching kit code. The GuildWar add-on is the working precedent
(`GuildWar/Scripts/GameData/GuildWarMapInfo.cs`).

## What the kit does not give us

**`WarpCharacterToInstance` is the wrong shape for a queue.** Reading its body
(`MapNetworkManager_PlayerActivity.cs:81`), it enforces three things a queue cannot satisfy:

- Participants must be in a **party** together.
- Only the **party leader** may trigger it; a member gets
  `UI_ERROR_PARTY_MEMBER_CANNOT_ENTER_INSTANCE` and is rejected (`:109`).
- Members must be **standing near the leader**, within `joinInstanceMapDistance` (`:95`).

A battleground queue is the opposite: strangers, not partied, scattered across different maps and
different map-server processes.

**And you cannot join an existing instance by ID.** The natural workaround — "spawn the instance,
then have everyone warp into that `instanceId`" — is closed off. The cluster **overwrites**
whatever `instanceId` you send:

```csharp
// ClusterServer.cs:496
// Generate a new instance ID, it won't being generated by map-server anymore
request.instanceId = _centralNetworkManager.DataManager.GenerateMapSpawnInstanceId();
```

Every `SpawnMap` request creates a **new** instance. There is no "join instance X" request type.

### The way through

The response to `SpawnMap` carries the instance's `peerInfo`, and `SaveAndWarpCharacterByPeerInfo`
takes a `peerInfo`. So the design is:

> Spawn **one** instance, keep its `peerInfo`, then warp **N** players to that same `peerInfo`.

The only obstacle is that `SaveAndWarpCharacterByPeerInfo` is `private`. It is not a problem:
`MapNetworkManager` is declared `partial`
(`MMO/Scripts/MMOGame/Networking/Map/MapNetworkManager.cs:16`, and four more partial files beside
it), and **all parts of a partial class share private access**. A file of ours in
`Assets/Scripts/` declaring `public partial class MapNetworkManager` can call the private method
directly, with no reflection and no kit edit.

This is the single load-bearing trick in the design. It is mechanism 1 from `EXTENDING.md` used at
full strength, and it is what makes the whole feature possible without patching `MMO/`.

## Architecture

The queue must be **cluster-side**. Players queue from many different map servers, so no single map
server can see the whole queue. The cluster is already the cross-server authority — it brokers
parties, guilds, chat and map users — so the queue belongs beside them.

```
  Client                Map Server A            Cluster Server           Instance (new process)
    |                        |                        |                         |
    |-- JoinQueue request -->|                        |                         |
    |                        |-- Enqueue ------------>|                         |
    |<-- "queued" ack -------|                        | [queue fills]           |
    |                        |                        |                         |
    |                        |                        |-- SpawnMap ---------->  |
    |                        |                        |<-- peerInfo ----------  |
    |                        |<-- WarpToBattleground -|                         |
    |                        |   (peerInfo + team)    |                         |
    |<-- MMOWarpMessage -----|                        |                         |
    |                                                                           |
    |========================= client reconnects to instance ==================>|
```

Map Server B, C, … receive the same `WarpToBattleground` message for their own local participants.
One instance, many source servers.

### Why `BaseGameNetworkManagerComponent` for 7 and 8

`BaseGameNetworkManagerComponent` (`Core/Scripts/Networking/BaseGameNetworkManagerComponent.cs`) is
a `MonoBehaviour` collected off the network manager's own GameObject at
`BaseGameNetworkManager.cs:112` (`GetComponents<BaseGameNetworkManagerComponent>()`), and then
driven through ~25 virtual lifecycle methods — `RegisterMessages`, `OnStartServer`,
`OnServerOnlineSceneLoaded`, `OnPeerDisconnected` and so on — each handed the manager.

It is strictly better than a `[DevExtMethods]` hook here: the overrides are compile-checked (no
silent string typos), the component is inspector-configurable, and it can be added to the instance
map's manager prefab **only**, so battleground match logic does not load on ordinary world servers.

Prefer it over hooks for anything that hangs off the network manager. Hooks remain the right tool
for entity-level reactions.

## Key mechanisms, in code

### The bridge that makes it work (component 6)

```csharp
// Assets/Scripts/Battleground/MapNetworkManager_Battleground.cs
namespace MultiplayerARPG.MMO
{
    public partial class MapNetworkManager
    {
        // Same partial class => private members are in reach. No kit edit, no reflection.
        public UniTask BattlegroundWarpToInstance(BasePlayerCharacterEntity entity, CentralServerPeerInfo peerInfo)
        {
            return SaveAndWarpCharacterByPeerInfo(entity, peerInfo);
        }
    }
}
```

### Registering the cluster handlers

Handler registration is public on `TransportHandler`
(`Core/LiteNetLibManager/Scripts/TransportHandler.cs:265`), and both `ClusterServer` and
`ClusterClient` inherit it. Neither needs a kit edit.

Cluster side — `ClusterServer` is **not** partial, but `CentralNetworkManager` is
(`MMO/Scripts/MMOGame/Src/Central/CentralNetworkManager.cs:18`) and exposes
`public ClusterServer ClusterServer { get; private set; }` (`:68`):

```csharp
public partial class CentralNetworkManager
{
    [DevExtMethods("OnStartServer")]                       // fires at CentralNetworkManager.cs:233
    protected void Battleground_OnStartServer()            // ClusterServer exists from :131
    {
        ClusterServer.RegisterRequestHandler<RequestEnqueueMessage, ResponseEnqueueMessage>(
            MMORequestTypes.BattlegroundEnqueue, HandleBattlegroundEnqueue);
    }
}
```

Map-server side — register in an `OnStartServer` hook, **not** `Awake`: `ClusterClient` is
constructed in `MapNetworkManager.Start()` (`:130`), so anything earlier sees a null.

### Carrying team assignment across the transfer

A participant is saved to the database and re-loaded by the instance process, so ordinary fields do
not survive. Use **custom character data**, which already persists and replicates (mechanism 7 in
`EXTENDING.md`) — set it on the source map server *before* calling the warp, because
`SaveAndWarpCharacterByPeerInfo` performs a full `TransactionUpdateCharacterState.All` save on the
way out:

```csharp
private static readonly int BgTeamKey = "BG_TEAM".GenerateHashId();

entity.SetServerInt32(BgTeamKey, teamIndex);   // server-only; clients never see raw team ids
await BattlegroundWarpToInstance(entity, peerInfo);
```

The instance reads it back in `OnServerOnlineSceneLoaded`. No schema change, no migration, no custom
network message. **Clear it when the match ends**, or a disconnected player carries a stale team
into their next battleground.

### Team spawn placement

Override `GetEnterMapPoint` on `BattlegroundMapInfo` (virtual at
`Core/.../BaseMapInfo.cs:291`) and branch on the stored team index. `GetRespawnPoint` (`:298`)
covers in-match respawns.

## Gotchas verified in the source

These were all read out of the kit, not guessed. Each one is cheap to design around now and
expensive to discover during testing.

1. **An empty instance kills itself after 30 seconds.**
   `MapNetworkManager.cs:167-173` calls `Application.Quit()` once an instance map has had zero
   players for `TERMINATE_INSTANCE_DELAY`, a `public const float` of `30f` (`:18`). The clock starts
   when the instance is told which map to run (`:1070`), not at process launch.
   *Consequence:* every participant must complete save-warp-reconnect inside 30 s of the instance
   coming up. Spawn the instance and issue the warp orders in the same step; never pre-spawn
   instances and hold them empty waiting for a queue to fill. The constant is `const`, so raising it
   would be a stock-kit edit — avoid needing to.

2. **`SaveCurrentMapPosition` must be `false`.** Default is `true`
   (`BaseMapInfo.cs:289`). If a battleground map saves position, a player who crashes or logs out
   mid-match is written into a map that no longer exists, and logs back in stranded.
   `GuildWarMapInfo.cs:55` already sets `false` for exactly this reason. Set
   `AutoRespawnWhenDead => true` alongside it (`:54`), as GuildWar does.

3. **Server code is compile-guarded.** Every server path in the MMO tree is wrapped in
   `#if (UNITY_EDITOR || UNITY_SERVER || !EXCLUDE_SERVER_CODES) && UNITY_STANDALONE`. Our code must
   match the same guard or client builds will break on symbols that are not there. The editor
   compiles both sides, which hides the mistake until a real build.

4. **Pick message IDs well clear of the kit's.** The highest `GameNetworkingConsts` value in use is
   194; `MMORequestTypes` runs to 15 and `MMOMessageTypes` to 13. All three are `partial`, so add
   ours from our own file — but start at **1000+** so a kit update adding new constants cannot
   collide. A collision here silently routes a message to the wrong handler.

5. **The queue must survive disconnects.** A player can queue and then log off, or their whole map
   server can drop. Drop stale entries from `OnPeerDisconnected` on the cluster and re-validate that
   every participant is still online immediately before spawning the instance — a match that pops
   for someone who left wastes an instance process and a 30-second window.

6. **`__GENERATING__` is a placeholder, not an ID.** The kit passes that literal string as
   `instanceId` when requesting a spawn (`MapNetworkManager_PlayerActivity.cs:125`) precisely
   because the cluster replaces it (`ClusterServer.cs:496`). Do not try to derive meaning from it or
   set your own.

7. **`BaseMapInfo` has four abstract members that decide all PvP targeting.**
   `IsPlayerAlly`, `IsMonsterAlly`, `IsPlayerEnemy` and `IsMonsterEnemy` are `protected abstract`
   (`Core/Scripts/GameData/MapInfo/BaseMapInfo.cs:330-333`), so `BattlegroundMapInfo` does not
   compile until all four are implemented. They are where teams are defined — `DamageableEntity`
   delegates every ally/enemy question to the current map (`DamageableEntity.cs:443`, `:450`).
   Implement them against a **public** custom-data team key, because ally checks also run on clients
   for nameplates and targeting. Worked example and the reasoning:
   [02_ARENA_1V1_2V2_DESIGN.md](02_ARENA_1V1_2V2_DESIGN.md), "The core problem: friend and foe".
   *(Added 2026-09-03; missed in the original draft.)*

8. **Instances do not load buildings.** `MapNetworkManager.cs:355` and `:407` skip building load and
   persistence when `IsInstanceMap()`. Anything a battleground needs must be in the scene or spawned
   at runtime; do not expect player-built structures.

## Build order

Ordered so the riskiest unknown is proven first, before any UI or content work is committed to it.

**Phase 0 — Wire the MMO entry scene.** Point `00Init_MMO.unity` at `GameDatabase_G.asset`,
`CanvasGameplay_G.prefab` and `TopDownAimController.prefab`, and get the four-server stack running
locally. Nothing below can be tested until this is done. This is worth doing regardless of the
battleground, since the MMO flavour currently diverges from the LAN one.

**Phase 1 — `BattlegroundMapInfo` + a test map.** Data class, one arena scene, two team spawn
points, registered in `GameDatabase_G`. Reachable via an ordinary warp portal to start with.
Verifiable on its own.

**Phase 2 — Prove the spawn→peerInfo→warp path with one player.** Consts, messages, the partial-class
bridge, and a trivial cluster handler that spawns an instance and warps the single requester into
it. **No queue, no teams, no UI — a GM chat command is enough to trigger it.**
This is the phase that validates the whole design. If `SaveAndWarpCharacterByPeerInfo` misbehaves
when driven from the cluster rather than from a party leader, it surfaces here, cheaply, before
anything is built on top.

**Phase 3 — The real queue.** Cluster-side queue with team-size targets, disconnect handling, and a
match-found step that spawns one instance and fans warp orders out to every participant's map
server. Team index written through custom character data.

**Phase 4 — Match logic.** `BattlegroundMatchComponent` on the instance manager prefab: team
assignment on arrival, score, timer, end conditions, rewards, and warping everyone back out.

**Phase 5 — UI and polish.** Queue window, estimated wait, pop notification, scoreboard,
leave-queue, and a rejoin grace period.

## Open decisions

Worth settling before Phase 3, not before Phase 2:

- **Team size and count.** Drives `BattlegroundMapInfo` fields and the match-found threshold.
- **Matchmaking bracket.** Level ranges? Any rating? Simple FIFO within a bracket is a fine start
  and can be replaced without touching the transport plumbing.
- **Party queueing.** Should a party queue together and be kept on one team? The kit's party data is
  already cluster-visible, so this is feasible, but it complicates team balancing.
- **Leaver policy.** Deserter debuff, backfill, or nothing.
- **Return destination.** Where a player lands when the match ends — the map they queued from
  (needs storing on the way in, another custom-data value) or a fixed town.
